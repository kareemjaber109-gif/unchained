# مواصفات مشروع kopo (KOPO)

تحديث: 30 سبتمبر 2026

## 1. المشكلة والأهداف

المشروع الحالي (Network Device Inventory) هو نظام CRUD بسيط لإدارة أجهزة الشبكة. يحتاج إلى تحسينات أمنية كبيرة، إضافة حقول جديدة، وإعادة تسمية، وإضافة معلومات تعليمية، بالإضافة إلى إصلاح الثغرات الأمنية الواضحة.

### الأهداف الرئيسية:
- تحسين الأمان لمنع الاختراق قدر الإمكان
- إضافة حقل VLAN لكل جهاز
- إضافة قسم معلومات جانبي عن أنواع الراوترات والسويتشات في Packet Tracer + الفروقات بينهم
- تغيير اسم المشروع بالكامل إلى "kopo"
- توفير بيانات دخول Admin واضحة وموثقة للمستخدم

### الأهداف غير المدرجة (Non-Goals):
- **لا** يتم تغيير قاعدة البيانات من SQLite (يظل كما هو للتطوير المحلي)
- **لا** يتم إضافة نظام تسجيل مستخدمين كامل (يستخدم Django Auth المدمج فقط)
- **لا** يتم عمل تكامل فعلي مع GNS3 أو Packet Tracer في هذه المرحلة (فقط معلومات تعليمية)
- **لا** يتم النشر على الإنترنت في هذه المرحلة

## 2. المتطلبات الوظيفية (Functional Requirements)

### FR-1: حماية كل الواجهات (Views) بتسجيل الدخول الإجباري
- المستخدم غير المسجل لا يستطيع الوصول إلى أي من صفحات: القائمة، الإضافة، التعديل، الحذف
- أي محاولة وصول بدون تسجيل تُحوّل تلقائياً إلى صفحة تسجيل دخول Django

### FR-2: إضافة حقل VLAN لنموذج Device
- الحقل جديد باسم `vlan_id` — نوعه عدد صحيح (IntegerField)
- المدى المقبول: 1 إلى 4094 (حسب معيار IEEE 802.1Q)
- يمكن أن يكون فارغاً/اختيارياً (للأجهزة اللي ملهاش VLAN)
- يظهر في: الفورم (Add/Edit)، الجدول الرئيسي، صفحة Admin، وملفات الاختبار

### FR-3: إعادة تسمية المشروع إلى "kopo"
- تغيير الاسم في شريط التنقل (Navbar)
- تغيير عنوان الصفحة (Title Tag)
- تغيير العناوين الرئيسية في الصفحات
- الاسم يظهر كـ **"kopo — Network Device Inventory"** أو باختصار **"KOPO"**

### FR-4: إضافة معلومات تعليمية عن الراوترات والسويتشات في Packet Tracer
- في الصفحة الرئيسية (Device List) - إضافة Sidebar / Card بجانب الجدول أو تحته تحتوي على:
  - قائمة بأشهر أنواع الراوترات في Cisco Packet Tracer (مثل 1841, 1941, 2811, 2901, 2911, ISR 4331) مع شرح مختصر لكل واحد
  - قائمة بأشهر أنواع السويتشات في Cisco Packet Tracer (مثل 2950, 2960, 3560, 3650, 2911) مع شرح مختصر
  - جدول صغير أو نقاط توضيح الفروقات الأساسية بين الراوتر والسويتش (طبقات OSI، الوظيفة، مثال استخدام)
- التصميم: باستخدام Bootstrap 5 (Accordion أو Cards بحيث يكون منظم ولا يشتت الانتباه)

### FR-5: توفير بيانات Admin موثقة للمستخدم
- المستخدم: `kopo_admin`
- كلمة المرور: `Kopo!Secure2026`
- يتم إنشاء المستخدم برمجياً + طباعة البيانات بوضوح للمستخدم

## 3. المتطلبات غير الوظيفية (Non-Functional Requirements / Security)

### SEC-1: إعدادات الأمان في settings.py
- تفعيل جميع وسائل الأمان التالية في settings.py:
  - CSRF_COOKIE_HTTPONLY = True
  - SESSION_COOKIE_HTTPONLY = True
  - SECURE_BROWSER_XSS_FILTER = True (أو CSP Header بديل)
  - SECURE_CONTENT_TYPE_NOSNIFF = True
  - X_FRAME_OPTIONS = 'DENY' (مفعلة فعلاً لكن نتأكد)
  - إضافة ميدلوير CSP (Content-Security-Policy) محدود
  - ADMIN_PATH تغييره من `/admin/` إلى مسار أقل وضوحاً مثل `/kopo-manage/` (مع الاحتفاظ بالقديم للرجوع أو فقط تغييره)
  - إضافة LOGIN_REDIRECT_URL و LOGOUT_REDIRECT_URL
  - إعداد AUTH_PASSWORD_VALIDATORS زيادة صرامة كلمات المرور (طول أقل 8 أحرف + مزيج)
  - إنشاء ملف `secrets.py` أو استخدام `django-secret-key` جديد عشوائي طويل

### SEC-2: إعدادات CSRF و Session
- CSRF_COOKIE_SECURE و SESSION_COOKIE_SECURE يتم تفعيلهم شرطياً حسب DEBUG (على الأقل عند الانتاج)
- SESSION_COOKIE_AGE = 3600 (ساعة واحدة فقط ثم تسجيل خروج تلقائي)
- SESSION_EXPIRE_AT_BROWSER_CLOSE = True

### SEC-3: الحماية من محاولات تسجيل الدخول المتكررة
- إضافة وسيلة لمنع Brute Force على صفحة تسجيل الدخول (باستخدام Django Axes أو cache-based rate limiting بسيط)
- إذا تعذر تثبيت مكتبات خارجية نستخدم طريقة بسيطة في الـ views

### SEC-4: تحسينات على Admin
- إضافة One-time passwords غير ممكنة، ولكن نضيف إعدادات:
  - إظهار آخر تسجيل دخول للمستخدم (لو أمكن)
  - أو على الأقل نضيف `AdminSite` مخصص مع عنوان مختلف

### SEC-5: إعدادات Headers الأمنية إضافية
- إضافة ميدلوير مخصص يضيف:
  - Strict-Transport-Security (HSTS) — في mode الإنتاج
  - Referrer-Policy: strict-origin-when-cross-origin
  - Permissions-Policy: geolocation=(), microphone=(), camera=()
  - X-Permitted-Cross-Domain-Policies: none

## 4. القيود والافتراضات

- Python 3.12 متوفر كما هو
- Django 6.1.1 مثبت كما هو في مجلد django_extracted (بدون إعادة تثبيت)
- لا نضيف مكتبات خارجية جديدة إلا إذا لزم الأمر (لتفادي مشاكل التثبيت السابقة)
- القوالب تبقى Bootstrap 5 CDN بدون تغيير للنظام البصري الأساسي
- اللغة تظل الإنجليزية في الواجهة، ولكن النصوص التعليمية عن Packet Tracer بالإنجليزية (مع كلمات عربية في الشرح إذا أمكن، أو كله إنجليزي واضح)

## 5. معايير القبول (Acceptance Criteria)

| الرقم | النوع | المعيار |
|-------|--------|---------|
| AC-1 | rule | محاولة فتح `/add/` بدون تسجيل دخول => توجيه تلقائي لصفحة تسجيل الدخول |
| AC-2 | rule | نموذج Device يحتوي على الحقل `vlan_id` بعد الهجرة ويمكن تخزين القيم 1-4094 |
| AC-3 | rule | شريط التنقل يعرض اسم "kopo" وليس "Network Inventory" القديم |
| AC-4 | rule | الصفحة الرئيسية تحتوي على قسم معلومات Packet Tracer مع أنواع الراوترات والسويتشات والفروقات |
| AC-5 | rule | يمكن تسجيل الدخول إلى /kopo-manage/ باستخدام: kopo_admin / Kopo!Secure2026 |
| AC-6 | rule | كل إعدادات الأمان في SEC-1..SEC-5 موجودة في settings.py أو ملفات مرفقة |
| AC-7 | rubric | جودة الأمان: 0-3 نقاط. العتبة: >=2 (0 = لا تحسينات، 1 = بعض، 2 = أغلبها، 3 = كلها + إضافات) |
| AC-8 | rule | `python manage.py check` يعيد "System check identified no issues" |
| AC-9 | rule | `python manage.py test devices` يمر بنجاح (بعد تحديث الاختبارات لحقل VLAN) |
| AC-10 | rule | صفحة Admin مسارها `/kopo-manage/` جديد يمكن الوصول إليه |

## 6. أسئلة مفتوحة (تم حلها)

- هل نحذف مسار `/admin/` القديم؟ **القرار:** نحوله إلى `/kopo-manage/` فقط
- هل نبقي DEBUG=True؟ **القرار:** نجعله شرطياً (يُقرأ من env مع default True للتطوير المحلي)، لكن كل إعدادات الأمان الأساسية تظل مفعلة حتى لو DEBUG=True الأجزاء اللي ممكنة
